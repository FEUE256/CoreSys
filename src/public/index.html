Chapter I — System Genesis

CoreSys begins execution at the boundary between firmware and operating system logic. The first active environment is UEFI, which provides controlled entry into system memory, device enumeration, and boot services.

From this point, execution transitions into a custom bootloader designed to remove legacy BIOS dependencies entirely. This ensures a deterministic boot path with no fallback to outdated compatibility layers.

After initialization, control is transferred to the kernel through an explicit entry interface. At this stage, the system is no longer firmware-controlled; it becomes fully self-managed.

Boot pipeline: (CIOS) -> UEFI → Bootloader → Init Layer → Kernel → User Mode

Chapter II — Boot Architecture

The boot architecture is responsible for constructing a stable execution environment before the kernel begins operation. This includes memory map acquisition, stack allocation, and interrupt policy initialization.

The system deliberately avoids legacy boot structures and instead relies on a minimal initialization chain designed for predictability and reproducibility across UEFI-compliant hardware.

Cyber::Boot exists as the historical foundation of this system. Its concepts have been restructured into CoreSys initialization routines, forming a cleaner separation between boot logic and kernel logic.

Chapter III — Kernel Model

The CoreSys kernel operates within a flat 64-bit address space. All memory regions are explicitly managed, with no implicit kernel-user blending or legacy compatibility assumptions.

System calls are routed through a minimal experimental API layer. This layer is intentionally small, focusing on extensibility and research flexibility rather than compatibility with existing operating systems.

Traditional POSIX interfaces are not implemented. This design decision removes historical constraints and allows direct exploration of alternative system abstractions.

Chapter IV — System Philosophy

CoreSys is not designed as a consumer operating system. It is structured as a research environment for understanding how operating systems behave at the lowest abstraction levels.

Every subsystem is replaceable, and every interface is treated as experimental. This allows the system to evolve without architectural lock-in or backward compatibility constraints.

The goal is not usability, but clarity: exposing the full structure of system design from firmware entry to user-space execution.

Distribution Layer

CoreSys is distributed as raw disk images intended for UEFI-based execution environments. These images contain bootloader, kernel, and early system components. Go to Guthub Releases to get the latest image; or compile from source.

Documentation Layer

System documentation is structured hierarchically, reflecting the actual execution model of the operating system.

It begins at firmware interaction, proceeds through boot initialization, continues into kernel execution, and ends at user-mode system interfaces.

Full documentation is available in the repository and is continuously updated as the system evolves.
